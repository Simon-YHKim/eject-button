무엇을 바꿨는가

Billing 9.1.0 및 API 이전
  • 버전 카탈로그를 9.1.0으로 올리고 artifact를 billing-ktx에서 billing core로 전환했다.
  • 첫 시도였던 billing-ktx:9.1.0은 이 프로젝트의 Kotlin 2.0 compiler가 더 최신 Kotlin metadata를 거부했다. 앱이 Billing KTX extension을 사용하지 않으므로 광범위한 Kotlin/Compose 업그레이드 대신 동일 PBL 9.1.0 Java core artifact를 택했다.
  • PendingPurchasesParams.enableOneTimeProducts(), QueryProductDetailsResult, 자동 서비스 재연결, 즉시 launchBillingFlow() 결과 및 PBL 9 sub-response 로깅을 반영했다.
  • ProductDetails를 foreground 복귀 때 다시 조회해 stale cache 위험을 줄였다.
구매·복원 회귀 방어
  • Play 복원이 OK일 때만 entitlement를 갱신하고, 네트워크/서비스 오류에서는 마지막 상태를 보존한다.
  • SUBS/INAPP의 목표 상품 중 PURCHASED이며 suspended가 아닌 구매만 grant·acknowledge한다.
  • 성공한 INAPP 복원에서 상품이 없으면 광고 제거 권한을 해제해 환불·취소와 동기화한다.
  • latest-request-wins generation과 in-flight token set으로 오래된 restore callback과 중복 acknowledge를 억제한다.
  • one-time offer가 하나면 표시 가격과 같은 offer token으로 결제한다. 동시에 eligible offer가 여러 개면 임의 선택하지 않고 안전하게 중단한다.
바이너리·CI 검증기
  • JDK 17 source-file 방식의 scripts/CheckAndroidBillingVersion.java를 추가했다.
  • APK/AAB의 canonical billing.properties 경로와 단일 billing_client 키를 강제하고 semver 하한·정확 버전을 검사한다.
  • APK binary XML과 AAB의 protobuf manifest를 각각 읽어 package/version을 검사한 뒤 두 산출물이 완전히 같은지 확인한다.
  • CI는 공식 bundletool 1.18.3을 SHA-256 a099…8e29로 고정 검증하고, release secret을 복원하기 전에 실행 준비를 마친다.
  • versionName workflow input은 환경변수와 allowlist regex를 거치며 Gradle/Java 인자를 인용해 shell injection 경로를 닫았다.

출시 흐름

남은 위험과 출시 게이트

  1. 조건부 blocker: Play Console의 eject_remove_ads_lifetime이 동시에 두 개 이상의 eligible one-time offer를 반환하면 앱은 안전하게 결제를 차단한다. 현재 릴리스에서는 단일 backward-compatible Buy option/eligible offer인지 먼저 확인한다.
  2. 실제 결제 QA: SUBS와 INAPP 각각 승인·취소·pending·재실행 복원·ITEM_ALREADY_OWNED·offline 보존·ack를 내부 트랙에서 검증한다.
  3. 운영 상태: 활성 Production은 아직 1088 (1.7.2)다. 1089+를 게시할 때까지 정책 알림은 유지된다.
  4. 기존 보안 부채: 구매 진위는 서버 검증 없이 client에서 entitlement를 부여한다. RTDN/Voided Purchases 기반 서버 검증은 후속 개선으로 분리한다.
  5. 기존 CI 공급망 부채: signing secret과 write token이 있는 release job에서 일부 GitHub Actions가 full commit SHA가 아닌 major tag를 사용한다. 이번 Billing 이전과 분리해 pinning/publish job 격리를 권장한다.

큰 화면·태블릿·폴더블 관련 Play 권장 조치 두 건은 의도적으로 수정하지 않았다.

GUI 작업용 프롬프트

아래 내용을 GitHub/Play Console에 로그인된 GUI 작업 세션에 그대로 전달한다.

역할: 비상탈출 Google Play Billing 9.1 출시 검증 담당자

대상 앱
- 앱명: 비상탈출 - 가짜 전화 알리바이
- 실제 package: com.simonykim.ejectbutton
- Play 앱 ID: 4974211650203902764
- 개발자 계정: 4795577270086966748
- 현재 Production: versionCode 1088 / versionName 1.7.2 / 177개 국가·지역
- 작업 브랜치: Simon-YHKim/chore-billing-lib-upgrade

안전 규칙
1. 2nd-B 저장소/앱은 절대 건드리지 않는다.
2. 큰 화면 관련 권장 조치 두 건은 이번 범위에서 수정하지 않는다.
3. 키·시크릿·결제 자격증명을 화면 캡처나 코드에 노출하지 않는다.
4. 내부 테스트를 통과하기 전 Production에 게시하지 않는다.
5. “Start rollout to Production” 또는 동등한 최종 게시 버튼 직전에는 반드시 Simon에게 명시적 확인을 받고 멈춘다.
6. 서비스 계정 자동화는 아직 없으므로 Play 업로드는 수동으로 진행한다.

A. GitHub GUI
1. Simon-YHKim/eject-button에서 위 브랜치의 PR을 연다.
2. 변경 파일이 BillingManager/Policy/tests/version catalog/release verifier/workflow/report 범위인지 확인한다.
3. PR 검증과 리뷰가 통과한 뒤에만 main으로 merge한다. main 직접 push는 하지 않는다.
4. merge 후 Actions → “Build Release AAB + APK” → Run workflow를 연다.
5. version_name은 1.7.3을 입력한다. workflow가 계산한 versionCode가 1089 이상인지 확인한다.
6. 다음 로그가 모두 PASS인지 확인한다.
   - unit tests
   - release AAB/APK build
   - verifier self-test
   - AAB와 APK 각각 billing=9.1.0
   - package=com.simonykim.ejectbutton
   - 두 artifact의 versionCode/versionName 일치
7. CI가 만든 AAB와 QA용 APK를 내려받고 run URL, commit SHA, versionCode, SHA-256을 기록한다.

B. Play Console 상품 구성 사전 점검
1. Monetize products에서 구독 eject_premium_monthly가 활성인지 확인한다.
2. one-time product eject_remove_ads_lifetime의 현재 사용자가 동시에 받을 eligible purchase option/offer 수를 확인한다.
3. 단일 backward-compatible Buy option 또는 eligible offer 1개면 계속한다.
4. eligible offer가 2개 이상이면 업로드를 중단하고 CLI 세션으로 돌아와 offer 선택 UI 구현을 요청한다. 임의로 상품 설정을 삭제하거나 바꾸지 않는다.

C. 내부 테스트 트랙
1. CI에서 받은 동일 AAB를 Internal testing 새 release에 업로드한다.
2. package, versionCode 1089+, versionName 1.7.3, Billing 9.1.0을 다시 확인한다.
3. license tester 계정과 Play Billing test instruments를 사용하는 실제 Play 설치본으로 아래를 검증한다.
   - SUBS 승인: premium grant, 광고 제거, acknowledge, 앱 재시작 후 복원
   - SUBS 취소: entitlement 불변/오류 없음
   - INAPP 승인: 광고 제거 grant, acknowledge, 앱 재시작 후 복원
   - INAPP 취소: entitlement 불변
   - pending one-time: 완료 전 grant/ack 없음, 완료 후 onResume에서 grant/ack
   - ITEM_ALREADY_OWNED: 자동 restore
   - offline/service 오류 restore: 기존 entitlement 보존
   - INAPP 환불/취소 후 성공한 Play 재조회: 광고 제거 entitlement 해제
   - 결제 UI 복귀 경쟁: grant 직후 entitlement가 다시 false로 튀지 않음
4. 테스트 구매가 acknowledge되지 않아 자동 환불되는 현상이 없는지 확인한다.
5. 각 항목의 기기/계정/시각/결과와 필요한 스크린샷을 남긴다. 실패가 하나라도 있으면 Production으로 가지 말고 재현 정보와 함께 중단한다.

D. Production 게시 — Simon 확인 후에만
1. Internal QA가 전부 통과한 증거를 Simon에게 보여 주고 게시 승인을 요청한다.
2. 승인 후 Production → Create new release에서 내부 테스트와 동일한 AAB를 선택한다.
3. 기존 177개 국가·지역 설정을 임의 변경하지 않는다.
4. versionCode가 현재 활성 1088보다 큰지, package와 서명이 기존 앱과 맞는지 확인한다.
5. 릴리스 노트에는 “Google Play Billing Library 9.1.0 compatibility and purchase recovery improvements” 정도의 변경만 적고 큰 화면 수정은 주장하지 않는다.
6. 최종 게시 버튼 직전에 다시 화면 상태와 대상 앱을 확인한다. Simon의 명시적 확인이 없다면 클릭하지 않는다.
7. 게시 처리 후 Production 활성 버전이 새 versionCode/1.7.3인지 확인한다.
8. 정책 화면에서 “앱에서 Google Play 결제 라이브러리 버전 8.0.0 이상을 사용해야 합니다” 알림이 닫혔는지 확인한다. 처리 지연이면 완료로 단정하지 말고 재확인 시각을 기록한다.
